## ⚠️ КОДИРОВКА — ОБЯЗАТЕЛЬНО

Все вызовы REST — **Python + `requests` + JSON-тело в UTF-8** (как в `fetch.py`).
PowerShell не использовать: ломает кириллицу и `KEYBOARD` у кнопок бота (инцидент 17.07).

```python
import os, requests
WEBHOOK = os.environ["BITRIX24_WEBHOOK_URL"].rstrip("/") + "/"

def b24(method: str, payload: dict) -> dict:
    r = requests.post(WEBHOOK + method + ".json", json=payload, timeout=120)
    r.raise_for_status()
    return r.json()
```

## Шаг 2 — Выборка лидов

**Выборку делает `fetch.py`** — вручную её не повторять. Ниже — логика фильтров,
чтобы понимать, откуда взялись группы; она реализована в `fetch_groups()`.

**День отчёта `REPORT_DATE` = вчера (МСК)** при утреннем прогоне.

Брать лид если выполняется ХОТЯ БЫ ОДНО из условий:

```
A) Закрыт в день отчёта
   DATE_CLOSED ∈ [REPORT_DATE 00:00 … REPORT_DATE+1 00:00)
   И STATUS_ID в финальных (CONVERTED, JUNK, "4", "7", "20")
   → анализируем итог: правильно ли закрыт
   Не DATE_MODIFY: gpt_transcripts сдвигает DATE_MODIFY у старых закрытых.

B) Открытый + дата следующего контакта = день отчёта
   UF_CRM_1599826765930 ∈ [REPORT_DATE 00:00 … REPORT_DATE+1 00:00)
   → должны были связаться в день отчёта

C) Открытый + нет даты следующего контакта
   + LAST_ACTIVITY_TIME ∈ [REPORT_DATE 00:00 … REPORT_DATE+1 00:00)
   → нет плана, активность зависла в день отчёта
   (пустую дату следующего контакта фильтровать в Python, не REST `=UF:""`)
```

Читать батчи по порядку, **все** до последнего:

```python
import json
from pathlib import Path

RUN = Path(".run/latest")
manifest = json.loads((RUN / "manifest.json").read_text(encoding="utf-8"))

openlines = manifest["openlines_scope"]        # False → переписки в батчах нет

for path in sorted(RUN.glob("batch_*.json")):
    batch = json.loads(path.read_text(encoding="utf-8"))
    for lead in batch["leads"]:
        ...  # шаги 4A → 5
```

сколько файлов `batch_*.json`; счётчики в отчёте должны сойтись с `manifest.counts`.

## Шаг 3 — Коммуникация по лиду (уже в батче)

Фаза 1 сложила всё, что нужно. Повторные REST-вызовы по звонкам и чатам делать **не надо**.

| Ключ в JSON лида | Что внутри |
|------------------|------------|
| `calls[]` | звонки: `date`, `type` (1=входящий, 2=исходящий), `duration`, `failed_code`, `activity_id`. Включая звонки, висящие на связанном контакте |
| `chats[]` | переписка: `connector`, `messages[]` с `date`, `author_id`, `text` (если `openlines_scope=true`) |
| `timeline` | факт звонков и чат-сессий из карточки: `calls[]` (в т.ч. `missed`), `chats[]` |
| `transcript` | текст разговора из `UF_CRM_GPT_TRANSCRIPT`; `transcript_source` = `lead` / `contact` / `empty` |
| `uf_gap`, `uf_gap_detail` | был ли длинный состоявшийся разговор без текста |
| `exist_check` | сводка: сколько звонков/чатов/записей таймлайна, `has_communication` |

> ✅ **Текст разговора — только из `transcript`.** Поле наполняет `gpt_transcripts.py` на DWH
> (09:00 и 18:00 МСК). Пусто → текста нет; браузер, `getCopilotTranscript` и `launchCopilot`
> **не** использовать (политика #24604, в облаке Chrome и нет).

#### 3-EXIST. ОБЯЗАТЕЛЬНАЯ проверка ФАКТА коммуникации

⛔ **Не пропускать.** Bitrix иногда привязывает звонок/чат к контакту, а не к лиду
(типично для `IS_RETURN_CUSTOMER=Y`) — тогда `calls`/`chats` пусты, а в карточке звонок есть.

**Живой инцидент 21.07.2026:** лиды #89342, #87944, #87800 помечены как «коммуникация не
зафиксирована», хотя реальные звонки (включая успешный 112-секундный разговор) были в таймлайне.

Проверка выполняется по данным батча, без REST:

```python
exist = lead["exist_check"]
tl = lead["timeline"]

has_contact = exist["has_communication"]          # звонки | чаты | таймлайн | текст
only_timeline = not lead["calls"] and not lead["chats"] and (tl["calls"] or tl["chats"])
# only_timeline=True → контакт БЫЛ: дата и длительность из timeline.calls
# (missed=True → пропущенный), текста может не быть
```

**⛔ ЗАПРЕЩЕНО писать в отчёте «коммуникации не было» / «звонков нет» / «нет ни одного
зафиксированного контакта», пока не проверены ОБА источника: `calls`/`chats` И `timeline`.**
Если контакт найден в таймлайне — у лида ЕСТЬ факт общения, даже без текста разговора.
Формулировка для такого случая: «звонок [дата, длительность] был, запись разговора недоступна».

### Если текста разговора нет

Ничего не «дорасшифровываем». Порядок:

1. `uf_gap=true` (был состоявшийся звонок ≥15 сек, текста нет) → лид идёт в блок
   «Разговор не расшифровался», выводы о содержании речи не делаем.
2. По переписке, фактам звонков, полям CRM и ссылкам 1С судить **можно** — эти данные есть.
3. Прогон не останавливаем.

⛔ `crm.timeline.ai.launchCopilot`, `getCopilotTranscript`, Chrome/CDP, SESSID — **не использовать**
(политика #24604). Массовая дорасшифровка не закрывает пробел и создаёт нагрузку;
канон доставки текста — `gpt_transcripts.py` на DWH.

### Переписка (WhatsApp, Telegram, Max)

Тексты в `lead["chats"][].messages` — уже отфильтрованы фазой 1 (без системных сообщений
и служебной разметки). Если `manifest.openlines_scope=false` — текстов нет вообще; тогда
у вебхука не хватает прав `im` + `imopenlines`, и это одна строка в лог прогона
(**не** в chat31598). Судить в этом случае только по фактам сессий из `timeline`.

### 4A. Есть ли текст разговора (R01) — канон с 2026-08-25

#### ТегиКЦ — подстраховка, не угадывание

Перед записью `UF_CRM_1706806189`:

1. Если поле уже заполнено оператором — **не трогать**.
